# 中英文混排语音输入方案

日期：2026-09-15。基于当前本地原型、既有混合语音样本和本轮补充实验。

后续更新：用户已选定 FireRedASR2-AED，现已设为默认模型并接入实验性热词解码，见 [FireRed 切换记录](firered-integration.md)。本文以下保留选型前的对照与设计依据。

## 1. 建议

采用 **中英混合 ASR → 双语个人词库 → 按片段生成纠错候选 → 统一选择 → 格式化**。中文拼音保留为中文纠错分支；英文需要拼写、词级读音、逐字母缩写及用户读音别名。

这类同一句话内切换语言的识别通常称为 code-switching，例如“这个 API 用 PostgreSQL，timeout 设成三十秒”。产品还要解决 `PostgreSQL` 的标准大小写、`API` 的逐字母读法、`timeout` 等代码词的原样保留。

建议先用一套中英模型识别完整短句，保留切换处的上下文。预先用语言检测把很短的中英文音频分别送给两个单语模型，会增加分段边界和上下文丢失的问题；它不是本项目第一版的必要步骤。这是工程建议，尚未在本项目比较双模型分段方案。

## 2. 本地证据

沿用前一轮两条句子、两个合成音色，共四条音频；对每个模型测试固定中文 / 自动语言 × 有热词 / 无热词。本轮新增 **32 次识别**，没有改变原词库或使用参考答案提示 ASR。

| 样本 | Qwen3-ASR-0.6B | Fun-ASR-Nano |
|---|---|---|
| Tingting：部署到 Cloudflare | 两种热词条件均保留 `Cloudflare` | 两种条件均保留 `Cloudflare` |
| Tingting：使用 Kubernetes 和 PostgreSQL | 两词及标准大小写均正确 | 无热词为 `kubernetes` / `Postgresql`；加热词为 `Kubernetes` / `PostgresSQL` |
| Eddy：部署到 Cloudflare | 无热词变为“小飞侠”；加热词找回 `Cloudflare`，但周边中文仍有错误 | 固定中文＋热词为 `Soulflare`；自动语言＋热词为 `Slogan数据库` |
| Eddy：使用 Kubernetes 和 PostgreSQL | 两个术语均未识对 | 两个术语均未识对 |

固定中文与自动语言共有 8 对结果：Qwen **8/8 完全相同**；Fun **4/8 完全相同**，变化没有增加英文术语命中。自动语言不是解决混排的开关；固定中文也并不必然禁止英文输出。

每种模式有 6 次英文术语出现机会。Qwen 无热词命中 3/6，加热词 4/6；Fun 忽略大小写时无热词 3/6，加热词 2/6。此处按完整英文字母串匹配；`PostgresSQL` 多出的 `s` 属于拼写错误，不是大小写或空格问题。

这只是两条模板的合成测试，TTS 英文发音没有真人听写复核，不能当成真实说话者的混排准确率。结果说明当前方案需要哪些模块，不足以确定最终模型排名。

复现命令（选择新输出文件名）：

```bash
.venv/bin/python scripts/benchmark_mixed_language.py --model qwen --output results/mixed-qwen-rerun.jsonl
.venv/bin/python scripts/benchmark_mixed_language.py --model fun --output results/mixed-fun-rerun.jsonl
```

证据：[Qwen 逐条结果](../results/mixed-language-qwen.jsonl)、[Fun 逐条结果](../results/mixed-language-fun.jsonl)、[统计摘要](../results/mixed-language-summary.json)。`.meta.json` 记录模型 revision、运行时、脚本及输入哈希。

## 3. 纠错层如何扩展

### 先召回实体，再按类型处理

| 内容 | 候选来源 | 选择原则 |
|---|---|---|
| 中文词、人名 | 汉字推导拼音、词库指定读音 | 同音与有限近音，加上下文；保留原候选 |
| 英文普通词 | 原始 ASR、英文拼写或读音候选 | 保留用户说出的语言，不自动翻译 |
| 英文产品名 / 技术词 | canonical 标准写法、书写别名、用户口述别名 | 词库支持且上下文相关时纠正，不能只按最近字符串强换 |
| `API` / `SDK` 等 | 逐字母读法与缩写表 | 合并字母时确认是缩写，保留歧义 |
| 变量、版本、数字、单位 | 专门的格式规则与口述约定 | 明确 `retry_count` 的下划线、版本号点号、数字含义 |

实体召回应跨书写系统：英文名可能已经被 ASR 写成汉字。如果一开始只允许在英文字母片段中寻找英文词，就无法修复这种错误。可以把用户认可的中文读音别名加入英文词条；第一版不必先训练一个统一的中英音素模型。

建议的词条结构示例：

```json
{
  "canonical": "PostgreSQL",
  "kind": "product",
  "written_aliases": ["postgresql", "postgres sql"],
  "spoken_aliases": ["Postgres", "Postgres Q L"],
  "contexts": ["数据库", "SQL", "查询"],
  "preserve_case": true
}
```

这是用户词库的设计示例，尚未接入当前加载器；`Postgres` 是否展开为 `PostgreSQL` 应是用户约定，不应擅自改变所有简称。中文口述别名也由用户提供或确认，避免凭空添加宽泛映射。

当前原型 `data/lexicon.json` 中的英文条目 `pinyin=[]`，只用于 ASR 热词。后置纠错目前只扫描汉字，因此尚不具备上述英文纠错能力。当前高层 ASR 接口也没有输出可用的候选声学分数；本阶段只能做保守文本规则，不能把文字相似度包装成声学置信度。

### 候选合并与最终格式化

候选应带原文位置、候选类型、匹配依据和标准拼写。中文与英文局部候选一起选择，避免重叠替换。多次出现的同一产品名保持一致，但出现不同名称或语境冲突时保留原文。

青简可以继续作为中文局部候选的实验打分器；本项目没有验证其英文或混排重排效果。若接通用双语文本模型整理句子，应保护英文名称、标识符、数字和否定词，只接受有依据的局部修改。

格式化最后执行：中英空格、标准大小写、标点、单位、去口头重复。口述一个完整标识符往往需要明确拼写方式，例如“retry 下划线 count”；仅听到“retry count”并不能确定它应是空格、下划线还是驼峰命名。

## 4. 模型选择

| 模型 | 本项目建议角色 | 证据边界 |
|---|---|---|
| Qwen3-ASR-0.6B | 当前 Mac 混排原型的首选基线 | 本机已运行，清晰样本的英文专名与大小写更完整；样本有限 |
| Qwen3-ASR-1.7B | 下一轮准确率对照 | 官方提供同系列更大型号；本机尚未测混排效果和延迟 |
| Fun-ASR-Nano | 保留速度 / 中文对照 | 已运行，之前整批短句更快；当前混排并未显示超过 Qwen |
| FireRedASR2-AED | 后续混排及候选验证对照 | 官方明确支持 code-switching，并提供词级时间戳与置信分；本机未部署 |

[Qwen 官方文档](https://github.com/QwenLM/Qwen3-ASR)提供多语言识别和强制 / 自动语言用法；[Fun 官方文档](https://github.com/QwenAudio/Fun-ASR)列出中英能力及热词接口；[FireRedASR2S 官方仓库](https://github.com/FireRedTeam/FireRedASR2S)明确列出 code-switching。支持多语言不等于已证明对所有切换频率、口音和英文专名都准确。

模型选择建议基于当前需求与有限证据，用户尚未确认最终生产选型。无需只为中英混排立即部署两套单语 ASR 常驻并行；先把现有混合模型和词库纠错的效果测清楚。

## 5. 下一轮应如何评测

需要真人录制以下不同类型：中文句子插入英文名、英文短语插入中文、整句切换、逐字母缩写、中文口音英语、代码标识符 / 版本号 / 数值、同音或近音干扰词，以及不含热词的负例。

分别记录：

- 中文 CER、英文 WER，以及按“中文逐字＋英文逐词”统一分词后的混合错误率 MER；固定数字和缩写的归一化规则。
- 英文专名命中和误插入，普通词识别与标准大小写 / 下划线等格式准确率分开。
- 语言切换处的漏词、错词；用户实际纠正次数和松键到最终上屏的等待。
- 每一层纠错的改好 / 改坏数量。纯中文主 CER 不足以反映中英混排体验。

录音先固定词库，调参和测试按会话或说话者分开。优先修复最常见、可重复的真实错误，再决定是否需要更大模型或独立英文读音分支。
